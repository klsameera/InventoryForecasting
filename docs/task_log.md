## 2026-08-16 — Phase 1 Foundation: catalog + inventory ledger

**Requested:** "Make this full app" against `docs/app_plan.md`, a ~90-section
architecture proposal for a full ML-powered inventory forecasting platform
(catalog, warehouses, sales, purchasing, suppliers, a separate Python ML
service, 10 build phases). Building the entire plan in one pass wasn't
realistic — it spans a different language/runtime (Python) and this project's
own rules require going module-by-module. Presented the phased breakdown to
the user via `AskUserQuestion`; they chose **Phase 1: Foundation** (the plan's
own phase 1, `app_plan.md:2637-2661`): Categories, Brands, Attributes,
Products, Variants, SKUs, Warehouses, Inventory, Stock movements/adjustments.
No ML, no Python, no Sales/Purchasing. Planned via `EnterPlanMode`/`ExitPlanMode`
before writing code; the approved plan is summarized below.

**Changed:** Nine new modules, full stack, following
`.ai/rules/module-checklist.md` / the `module-generation` skill's Facade →
Service → thin Controller pattern:

- **Schema** — 11 new migrations: `categories` (self-referencing `parent_id`),
  `brands`, `attributes` + `attribute_values`, `products`,
  `product_variants` + `variant_attribute_values` (pivot), `skus`,
  `warehouses`, `inventories`, `stock_movements`.
- **Models** — `Category`, `Brand`, `Attribute`, `AttributeValue`, `Product`,
  `ProductVariant`, `Sku`, `Warehouse`, `Inventory`, `StockMovement`, plus a
  typed pivot `VariantAttributeValuePivot` (for Larastan, see below). Two new
  backed enums, `App\Enums\ProductType` and `App\Enums\MovementType`
  (`isInbound()`, `manualEntryCases()`).
- **Backend** — a `Service` + `Facade` + `Controller` + `Resource` (+ 2
  `FormRequest`s where the module writes) per module under
  `domain/Services/`, `domain/Facades/`, `app/Http/{Controllers,Resources,Requests}/`.
  `Inventory` and `StockMovement` deliberately have a reduced route/file set
  (see Key decisions).
- **Routes** — new `routes/modules.php` (required from `web.php`), one
  `Route::middleware(['auth', 'verified'])` block, all nine modules.
- **Frontend** — 24 pages under `resources/js/pages/{Module}/` (`index`/
  `create`/`edit`, or `index`/`all` only for `Inventory`, `index`/`create`
  only for `StockMovement`), all built from the existing UI kit — no new
  components. New shared pieces: `resources/js/hooks/use-debounced-value.ts`
  (search-box debounce, reused by every listing page) and
  `resources/js/types/catalog.ts` (all nine modules' TS types + `Option`
  types). `app-sidebar.tsx` gained **Catalog** and **Inventory** nav groups.
- **Tests** — `tests/Feature/{Category,Brand,Attribute,Product,ProductVariant,Sku,Warehouse,Inventory,StockMovement}Test.php`
  (55 tests), plus a factory per new model.
- **Docs** — `app_architecture.md` §1 gained §1a–§1d documenting the module
  list and every non-obvious pattern below; `app_guide.md` gained a "Catalog &
  Inventory" features section, an updated test-coverage table, and a rewritten
  §7 "Not built yet".

**Key decisions:**

- **Two modules deviate from the standard 8-route/12-file shape, on purpose**
  (`app_plan.md` §14, §88): `Inventory` is **read-only** (`index`/`all` only —
  it's a derived balance table, never written to directly). `StockMovement` is
  **append-only** (`index` + `create`/`store` only, no edit/update/delete —
  `StockMovement::UPDATED_AT = null`, migration has only `created_at`).
  `stock_movements.movement_type` carries all eleven types from the plan so
  the schema doesn't need a migration when Sales/Purchasing/Transfers land
  later, but the create form and `CreateStockMovementRequest`
  (`Rule::enum(MovementType::class)->only(MovementType::manualEntryCases())`)
  only allow the five with a manual entry point today: `OPENING_STOCK`,
  `ADJUSTMENT_IN`, `ADJUSTMENT_OUT`, `DAMAGE`, `WRITE_OFF`.
- **`StockMovementService::store()` is the only write path that touches a
  balance.** It creates the ledger row, then calls
  `InventoryFacade::applyMovement(...)` inside the same transaction —
  `applyMovement()` doesn't open its own transaction, it relies on the
  caller's, matching "call the other Facade instead of duplicating logic."
  `applyMovement()` locks the row (`lockForUpdate()`), rejects an outbound
  movement that would take `on_hand_qty` negative, and on an inbound movement
  with a `unit_cost` rolls `average_cost` forward by weighted average.
  `reserved_qty`/`incoming_qty` exist in the schema (plan §13) but stay `0` —
  nothing populates them until Sales/Purchasing exists.
- **`AttributeService` and `ProductVariantService` sync nested child rows**
  instead of `attribute_values`/`variant_attribute_values` being their own
  modules — `values: [{id?, value, sort_order}]` and `attribute_values:
  [{attribute_id, attribute_value_id}]` respectively, inside the same
  transaction as the parent write. `AttributeService` additionally guards:
  removing a value still referenced by a variant fails the whole update.
  Frontend pattern (both `create.tsx`/`edit.tsx` pairs): a `useState` array
  controls how many row-groups render; each row's own inputs stay uncontrolled
  (`values[0][value]`) so Laravel parses the submit as an array. `ProductVariant`'s
  attribute select is the one row input that must be controlled, because
  picking an attribute filters which values the next select offers.
- **Cross-module dropdown data goes through small `options()` Service
  methods** (`Category::options()`, `Product::options()`,
  `ProductVariant::optionsForProduct()`/`allOptions()`, etc.), called from the
  *other* module's Controller and passed as an Inertia prop — not through a
  client-side fetch to `{module}.all()`. `all()`/`get()` still exist (route-name
  contract, module-checklist) but aren't called by any Phase 1 page.
- **`store()`/`update()`/`delete()` redirect with a flashed toast; they do not
  return `response()->json(...)`**, despite that being what the
  module-generation skill's own template shows. Reason, discovered by testing
  in-browser and reading the Inertia source: `<Form>`/`router.delete()`
  require an Inertia-protocol response; a raw JSON response has no
  `X-Inertia` header, so Inertia's client falls back to an unstyled full-page
  load of the JSON. Matched the one pattern already proven in this codebase —
  `Settings\ProfileController::update`'s `Inertia::flash('toast', [...])` +
  `to_route(...)`, picked up automatically by the `useFlashToast()` hook
  already mounted in `AppLayout`. `all()`/`get()` stay `JsonResponse` — fine,
  since nothing routes them through Inertia.
- **Roles/permissions explicitly excluded**, even though the plan's own Phase
  1 lists them: no permission package is installed
  (`.ai/rules/architecture.md` already documents this), and installing one is
  a dependency change needing separate approval. All nine modules' routes are
  `auth` + `verified` only.
- **`routes/modules.php` instead of appending to `web.php`.** The
  module-checklist says to append to `web.php` directly; nine modules made
  that impractical. A dedicated required file is already this project's own
  pattern (`settings.php`), so this is a scale adaptation, not a new
  convention.
- **No synthetic "default variant" for simple products.** `skus.product_variant_id`
  is nullable per the plan's own schema, so a simple product's SKU is created
  directly with `product_variant_id = null`; only configurable products get
  `ProductVariant` rows first.

**Affected files:** too many to list individually — see the module list above.
Representative paths: `database/migrations/2026_08_15_1532{40..50}_*.php`,
`app/Models/{Category,Brand,Attribute,AttributeValue,Product,ProductVariant,VariantAttributeValuePivot,Sku,Warehouse,Inventory,StockMovement}.php`,
`app/Enums/{ProductType,MovementType}.php`,
`domain/{Services,Facades}/{Module}{Service,Facade}/*.php` (×9),

**Implementation details (bugs found and fixed during this task, worth
knowing before touching this code again):**

- **A `JsonResource` passed directly into an `Inertia::render()` prop gets
  Laravel's default `{"data": {...}}` wrap** — discovered because
  `Warehouse/edit.tsx` rendered "Edit undefined" with every field blank. Every
  single-record prop (`edit()`'s `'warehouse' => new WarehouseResource($model)`)
  now calls `->resolve()` instead — collections already did this correctly
  via `->through(fn ($m) => (new XResource($m))->resolve())`.
- **`$request->only([...])` returns `[]` when none of the keys are present in
  the query string, and PHP's empty array JSON-encodes as `[]`, not `{}`.**
  On first page load (no filters yet), `filters.sort` on the frontend resolved
  to `Array.prototype.sort` (inherited from `Array.prototype`) instead of
  `undefined` — which then serialized the native function's `.toString()`
  into the next `router.get()` request's query string
  (`?sort=function%20sort()%20%7B%20%5Bnative%20code%5D%20%7D`). Fixed by
  casting `'filters' => (object) $filters` in every `index()`. Caught via a
  real browser search interaction, not by the type checker (PHP↔JS boundary,
  invisible to `tsc`).
- **`ProductVariant`'s index listing showed "null: 42" instead of "Size: 42"**
  for the Attributes column — `ProductVariantService::all()` eager-loaded
  `attributeValues:id,attribute_id,value` but not the nested
  `attributeValues.attribute:id,name`, so `attribute_name` resolved to null
  outside the single-record `get()` path (which did eager-load it). Fixed by
  adding the nested eager-load to `all()` too.
- **Boolean `status`/`forecast_relevant` checkboxes need a preceding
  `<input type="hidden" name="status" value="0">`** — an unchecked HTML
  checkbox submits nothing at all, and the FormRequest rule is
  `['required', 'boolean']`, so unchecking "Active" would fail validation
  with a missing-field error instead of saving `false`. Standard
  hidden-then-checkbox pattern, same `name`, PHP keeps the last value in
  submission order.
- **Larastan (level 7) needed three fixes, none of them suppressions** (the
  tool explicitly forbids `@phpstan-ignore`/baselines and none were used):
  1. Every Resource needed `@mixin {Model}` so Larastan resolves
     `JsonResource::__get()`'s proxying to the wrapped model's properties.
  2. Every Service's `all(): LengthAwarePaginator` needed to import the
     **concrete** `Illuminate\Pagination\LengthAwarePaginator`, not the
     `Illuminate\Contracts\Pagination\LengthAwarePaginator` interface — only
     the concrete class declares `->through()`, which every `index()`/`all()`
     controller method uses.
  3. `ProductVariant::attributeValues()`'s pivot carries a denormalized
     `attribute_id` column beyond the two FKs, which the generic anonymous
     `Pivot` class doesn't expose. Added `App\Models\VariantAttributeValuePivot
     extends Pivot` with `@property int $attribute_id`, wired via
     `->using(VariantAttributeValuePivot::class)`, and the relation's
     `@return` docblock needed all four `BelongsToMany` generic type
     parameters (`<AttributeValue, $this, VariantAttributeValuePivot, 'pivot'>`)
     since the template isn't covariant.
- Wayfinder's `php artisan wayfinder:generate` needs `--with-form` to emit
  `.form()` variants — running it bare (as the CLI reference implies) silently
  omits them even though `vite.config.ts` has `formVariants: true` (that
  config only applies to the Vite-plugin code path, not the artisan command).
  Every `<Form {...Controller.action.form()}>` in this task depends on having
  run it with the flag.
- Playwright MCP's browser binary ("chrome-for-testing") was not installed on
  this machine, separately from the `playwright` npm package/Chromium
  installed in the prior session — `npx @playwright/mcp install-browser
  chrome-for-testing` (~300MB download) was required before any
  `mcp__playwright__*` tool call would work.

## 2026-08-16 — Phase 2: Sales and purchasing

**Requested:** "continue until all phases done" — the user asked to proceed
through the remaining phases of `app_plan.md` without stopping to re-confirm
scope each time. This entry covers Phase 2 (§78: Sales, Returns, Suppliers,
Purchase Orders, Goods Receiving, Stock Transfers, Inventory Batches), built
and verified with the same rigor as Phase 1 — schema design, build in
dependency order, automated tests, full browser E2E walkthrough, docs, this
entry. Phases 3–10 (deterministic analytics through the Python ML service)
remain explicitly out of scope for this entry — see Open/not done.

**Changed:** Seven new modules — `Supplier`, `PurchaseOrder`, `GoodsReceipt`,
`StockTransfer`, `SalesOrder`, `SalesReturn`, `InventoryBatch` — plus a
significant extension of the Phase 1 stock-movement infrastructure to be the
shared write path every one of them uses.

**Key decisions (including rejected alternatives and why):**

- **New shared write path, not five copies of the same logic.**
  `StockMovementService::store()` (the Phase 1 manual-adjustment path) was
  split into `store()` (validates `MovementType::manualEntryCases()`, opens a
  transaction, delegates) and a new public `post()` (no manual-entry
  restriction, no own transaction — the actual ledger write + balance +
  batch side effects). Every Phase 2 write that touches stock calls
  `StockMovementFacade::post()` inside its own transaction. Rejected:
  duplicating "create ledger row + call `InventoryFacade::applyMovement()`"
  inside each of `GoodsReceiptService`, `SalesOrderService`,
  `StockTransferService`, `SalesReturnService` — violates the project's own
  "never duplicate logic between services" rule and would have meant fixing
  the same bug five times (see the `*_number` NOT NULL bug below, which
  *did* have to be fixed five times because it wasn't behind a shared path).
  Full design in `app_architecture.md` §1e.
- **New `InventoryBatch` module for FIFO lot tracking**, wired into `post()`
  so it applies to Phase 1's manual adjustments too, not just Phase 2 writes
  — an `OPENING_STOCK`/`ADJUSTMENT_IN` movement now also opens a batch, and
  `ADJUSTMENT_OUT`/`DAMAGE`/`WRITE_OFF` consume FIFO. This was a deliberate
  scope decision: `app_plan.md` §23 says ageing must be calculated against
  actual stock batches, and restricting batch-opening to only
  Purchase-Receipt-sourced stock would make ageing wrong for anything
  adjusted in manually. `consumeFifo()` is best-effort (stock predating
  batch tracking has no batch to draw from) so this didn't break any
  existing Phase 1 behavior — confirmed by re-running the full Phase 1 suite
  after the change, 94/94 still green.
- **`unit_cost` backfill on outbound movements.** `post()` now writes the
  FIFO-consumed weighted cost back onto the movement row when the caller
  didn't supply one (true for Sales, Transfers, Damage/WriteOff — none know
  a cost up front). `SalesOrderService::confirm()` reads this back as
  `sales_order_items.cost` for margin reporting;
  `StockTransferService::receive()` reads it off the matching `TransferOut`
  row so the destination batch opens at the correct carried cost.
- **Status-workflow documents (`PurchaseOrder`, `StockTransfer`,
  `SalesOrder`) instead of forcing everything into the flat 8-route module
  shape.** Each is Draft-editable only, with dedicated transition methods
  (`approve()`, `cancel()`, `markOrdered()`/`dispatch()`/`receive()`/
  `confirm()`) rather than overloading `update()` to also mean "change
  status." `GoodsReceipt` and `SalesReturn` are immutable/posted-on-create
  instead — same shape as Phase 1's `StockMovement`, since both write
  straight to the ledger with no draft state. Documented in
  `app_architecture.md` §1f.
- **No `Customer` module.** `app_plan.md` §16 references `sales_orders.
  customer_id nullable` but never defines a `customers` table anywhere in
  the document, and Phase 2's own roadmap (§78) doesn't list a Customer
  module. Built `customer_name` as a plain nullable string instead of
  inventing a table/module the plan never specified — matches the project
  rule against building beyond what's asked. If CRM is wanted later, it's a
  new module with its own migration replacing the column.
- **No `SupplierPerformanceMetrics` and no Purchase Returns module.**
  `app_plan.md` §21's supplier-performance table and a supplier-facing
  return flow both exist in the plan's schema thinking but neither is listed
  in Phase 2's own roadmap (§78 lists exactly: Sales, Returns, Suppliers,
  Purchase Orders, Goods Receiving, Stock Transfers, Inventory Batches).
  `PURCHASE_RETURN` stays in the `MovementType` enum, unused, for a future
  phase to post programmatically.
- **`supplier_skus` is a nested child of `Supplier`** (like Phase 1's
  `attribute_values` under `Attribute`), not its own module — it only makes
  sense scoped to a supplier. Cross-supplier `is_primary` uniqueness (only
  one supplier can be primary for a given SKU) is enforced at the Service
  layer (`SupplierService::syncSupplierSkus()` clears the flag on other
  suppliers' rows for that SKU), not a DB constraint, because it's a
  cross-row invariant a unique index can't express directly.
- **Recompute `incoming_qty` from scratch, don't increment/decrement it.**
  `PurchaseOrderService::recalculateIncoming()` sums outstanding
  (quantity − received) across a SKU's open POs in a warehouse every time,

## 2026-08-16 — Phase 4: the data pipeline

capture job plus a read-only history page with a manual trigger. This is

**Key decisions (including rejected alternatives and why):**

- **One table covers all three of Phase 4's roadmap bullets.** app_plan.md
  §80 lists "Daily snapshots, Demand aggregation, Stockout history" as three
  separate items, but §15's own schema for `inventory_daily_snapshots`
  already carries a `sold_qty` column (the demand aggregation) and
  `stockout_flag`/`stockout_minutes` columns (the stockout history) — there
  was nothing left for two more tables to hold. Building
  `demand_daily_aggregates` and `stockout_history` tables alongside it would
  have been duplicating data the one table already has. Rejected explicitly
  once §15 was re-read carefully rather than assumed from the roadmap
  bullet list alone.
- **Every figure is reconstructed from `stock_movements`, never accumulated
  as a running total.** `captureDay()` computes closing quantity as the net
  signed sum of every movement up to that day's boundary (with the previous
  day's own snapshot as a shortcut when available, falling back to a full
  ledger replay otherwise). This means capturing — or *re-capturing* — any
  date, including a backfill from months ago, is always correct on its own
  terms, with no dependency on captures having happened in date order. A
  running-total design was considered and rejected: it would make backfills
  and re-corrections fragile (every subsequent day would need recomputing
  too), which is exactly the kind of bug this design avoids by construction.
- **`stockout_minutes` is computed by replaying the day's movements in
  timestamp order**, not estimated from opening/closing quantities alone —
  §15 explicitly calls this "extremely important for ML" (telling "no
  demand" apart from "no stock to sell" apart), so an approximation wasn't
  good enough. The replay is bounded by `min(end of day, now())` so that
  capturing an in-progress "today" never counts not-yet-happened movements.
- **`inventory_value` uses current `average_cost`, not a historical
  point-in-time cost.** Reconstructing what the weighted-average cost was on
  an arbitrary past date would mean replaying the full cost-averaging
  algorithm from the ledger for every snapshot — a real feature, but not one
  this phase's stated scope asked for. Documented as a simplification, same
  category as Phase 3's turnover-ratio one.
- **The nightly schedule always captures *yesterday*, never today** — a day
  isn't complete until it's over, so a snapshot taken mid-day would be
  wrong the moment more movements happen later that day. The manual
  "Capture snapshot" button (and the console command's optional `{date}`
  argument) exists specifically for backfilling or checking today's
  in-progress numbers without waiting.
- **Read-only + one `capture` action, not the standard 8-route module
  shape.** There's no user-editable record here at all — every field is
  derived. Modeled after `InventoryBatch` (§1e) rather than any writeable
  module.

no model; `ForecastRun`; `Forecast`), the four `ml_*`/`forecasts` tables from

`ml-service/` — a FastAPI Python service with a labeled, non-ML statistical
baseline, its own README, and its own `pytest` suite.

**Key decisions (including rejected alternatives and why):**

- **Scaffold with an honest baseline, not real ML and not a stub that
  errors.** Two alternatives were considered and rejected: (a) skip Phase 5
  entirely and jump to Phase 6, which would leave the plan's own required
  architecture (Laravel↔Python contract, job-based processing, the schema)
  unbuilt and harder to retrofit later; (b) fabricate "realistic-looking"
  forecast numbers from invented sample data, which is exactly what the

  request.** `ForecastRunService::store()` only creates the `Queued` row and
  dispatches `RunDemandForecast`; all the real work is in `processRun()`,
  called only from the Job. This is app_plan.md §32's own instruction

  than synchronous HTTP calls"), and it's also why the queue worker
  (already running as part of `composer dev` since Phase 1, but idle until
  now) is suddenly load-bearing — `server_architecture.md` §5 updated to
  say so.
- **Laravel pre-aggregates before calling Python; Python never touches the
  database.** `MlServiceClient::buildSeries()` reads up to 180 days of

  (Phase 4) and sends a compact time series, not raw ledger rows —
  app_plan.md §35 explicitly warns against pushing large datasets over HTTP.
  This is also why Phase 5 could not have come before Phase 4: there was no
  aggregated daily history to build a series from until the snapshot
  pipeline existed.
- **`processRun()` is not wrapped in one outer transaction.** A batch can
  cover many warehouse/SKU pairs; if the ML call or a later `forecasts`

  the row a future trained model would replace by inserting its own version
  instead — no schema change needed when that day comes.

**Key decisions (including rejected alternatives and why):**

- **A 3-tier fallback hierarchy (category+size → brand+category →

- **Maturity is a live classification, never persisted.** Considered adding

  app (ABC class, movement speed, days of stock) is likewise recomputed on
  demand rather than cached — consistent with that established pattern
  rather than introducing a new one. `forecast_source` on the persisted
  `Forecast` row already tells a reader which tier was actually used for
  any given forecast, which is the part worth keeping a record of.
- **`EndOfLife` is evaluated independently of the history-based tiers, not

  series-selection logic still treats it like Established/Mature/Declining
  for the purpose of "use its own history" — only Cold-start/Early actually
  change which series gets sent.
- **The Early-maturity blend uses one fixed weight (30% own / 70%
  fallback), not app_plan.md §29's more elaborate multi-factor illustration**
  (SKU data / category+size data / brand+category data / seasonality,
  independently weighted). This scaffold has no separate seasonality signal
  to weight in, and §29 itself says "you shouldn't necessarily hard-code
  these exact percentages; models can learn them" — a single documented
  constant is the honest, basic version of that idea, matching the same
  "basic version first" precedent as Phase 3's reorder point.
- **`forecast_relevant` (an unused Phase 1 `attributes` column) is what
  identifies a "size" dimension, not a hardcoded attribute name like
  "Size."** Checked the schema before assuming a new column was needed —
  `app_plan.md` §5's own Attribute field list already includes
  `forecast_relevant`, and it was sitting unused since Phase 1's own
  Attribute module shipped a full UI checkbox for it. Using it means any
  attribute an admin flags as forecast-relevant (Size, Color, Pack size, …)
  participates in the category-size tier automatically, with no code change
  — a real, working generalization the plan's own schema already
  anticipated, not scope creep.
- **`ForecastMaturityService::classify()` reads `stock_movements.occurred_at`,
  not `created_at`.** The ledger carries both (`occurred_at` is the business
  transaction time; `created_at` is when the row was written, which can
  differ for backfills/corrections) — caught by reading the actual
  migration before writing the query, not assumed from the column name
  alone, avoiding a repeat of earlier phases' date-column mistakes.
- **No new page or route for `DemandProfileService`'s category-size/

  these as ML/backend concepts the forecasting pipeline consumes, not

## 2026-08-16 — Phase 7: inventory optimization (the decision engine)

**Requested:** Sixth continuation of "continue until all phases done."
Phase 7 (app_plan.md §83): stockout prediction, dynamic safety stock,
reorder point, recommended quantity, recommended purchase date, MOQ
support, pack-size support, supplier lead-time support. Unlike Phase 5,
this phase needed no `AskUserQuestion` — app_plan.md §40's decision-engine
formula is deterministic arithmetic over data that already exists (forecast,
stock and supplier terms), not something requiring a trained model, so
there was no placeholder-vs-real conflict to resolve.

**Changed:** One new module, `InventoryRecommendation` — writes
`inventory_recommendations` (app_plan.md §52), computing app_plan.md §40's
full formula per warehouse/SKU pair and exposing a four-action human
override workflow (review/accept/modify/reject, app_plan.md §53). The
project's third scheduled task, `app:generate-inventory-recommendations`.

**Key decisions (including rejected alternatives and why):**

- **MOQ and pack-size "support" meant using existing columns, not adding
  schema.** `supplier_skus.minimum_order_qty`/`order_multiple`/
  `expected_lead_time_days` were all built in Phase 2 but never read by any
  Service until now. Checked the schema before assuming new columns were
  needed — app_plan.md §83's "MOQ support"/"Pack-size support"/"Supplier
  lead-time support" bullets are satisfied entirely by finally consuming
  data that already existed, the same "check before assuming a gap" move
  Phase 6 made with `attributes.forecast_relevant`.
- **Only `RecommendationType::Purchase` is produced.** app_plan.md §51 lists
  nine action types; the other eight are overstock/ageing/clearance-driven
  and explicitly Phase 8's territory ("ageing prevention"). Reserved the
  same way Phase 5 reserved five of six `ForecastSource` values for Phase
  6 — the enum and the `overstock_risk`/`ageing_risk` columns exist
  (matching app_plan.md §52's full schema) but stay unpopulated, not
  invented ahead of the phase that needs them.
- **A recommendation requires a completed forecast to already exist.**
  `InventoryRecommendationService::generate()` silently skips any pair with
  no `forecasts` row — no fallback to historical velocity, no invented
  number. This is the same "no placeholder data" discipline applied
  structurally rather than needing a special-case decision: it's also why
  Phase 7 could not have come before Phase 5/6 existed to produce forecasts
  to build on.
- **Dynamic safety stock (app_plan.md §44) is real, computed from actual
  demand variability** — `z × demand_std_dev × √lead_time_days`, with
  `demand_std_dev` from 90 days of real `inventory_daily_snapshots.sold_qty`,
  falling back to Phase 3's original flat `daily_rate × 7 days` only when
  there's fewer than two data points to compute a standard deviation from.
  **`z` is one fixed ~95% service level for every SKU**, not app_plan.md
  §45's per-ABC-class levels (A 98%/B 95%/C 90%) — classifying ABC per-SKU
  as a reusable lookup (today it only exists inline inside
  `InventoryAnalyticsService`'s own paginated report) was judged a
  separate, later refinement rather than something to entangle with this
  phase. Documented as a known gap, not silently dropped.
- **`InventoryAnalyticsService`'s own (Phase 3, flat-safety-days) reorder
  point was deliberately left alone, not merged into the new engine.** The
  two now compute slightly different reorder points for the same SKU. Left
  as two honestly-labeled, not-yet-unified calculations rather than risk
  regressing Phase 3's already-shipped, already-tested report by reaching
  into it — reconciling them is future work, called out in `app_guide.md`
  §7 so it isn't mistaken for a bug.
- **Rejected an initial design where `generate()` only checked for an
  existing *open* recommendation before creating a new one.** A live
  Playwright walkthrough (see Verification) caught the real consequence
  immediately: an Accepted/Modified/Rejected recommendation for a pair that
  was still urgent got a *second*, duplicate `NEW` row on the next
  `generate()` run — confusing, and a real behavioral bug, not just a test
  assumption. Fixed by skipping a pair entirely if *any* row already exists
  for it, open or decided. This makes a human decision effectively terminal
  for that pair until some future signal (like a completed purchase order)
  reopens it — a real, documented Phase 7 limitation, not a hidden one.
- **No "Create PO" / "Bulk Create PO" integration** (app_plan.md §61's
  screen mockup shows these as example actions). §83's own "Add:" list for
  Phase 7 doesn't require it, and building a real prefill integration would
  have meant extending Phase 2's `PurchaseOrder/create.tsx` to accept
  query-string prefill data it doesn't support today — scope the phase
  didn't ask for. Accept/Modify/Reject (§53's actual, explicit ask) are
  built; turning a decision into a real PO is a natural next step, not
  done here.
- **`applyDecision()` is a small shared private helper** wrapping the
  transaction/catch/log/envelope boilerplate common to
  `review()`/`accept()`/`modify()`/`reject()` — the one deliberate
  abstraction in this Service. Four near-identical try/catch blocks were
  judged worth collapsing once; everything else in the Service stays
  concrete per the project's "no premature abstraction" rule.
- **The Controller passes `$request->user()?->id` into the Service**

## 2026-08-16 — Phase 8: ageing prevention

**Requested:** Seventh continuation of "continue until all phases done."
Phase 8 (app_plan.md §84): future ageing prediction, overstock prediction,

**Changed:** No new module. `InventoryRecommendationService::buildRecommendation()`
(Phase 7) was restructured to compute ageing/overstock signals for every
pair with a forecast, and to decide between five recommendation types
(`Purchase`, `ReducePurchase`, `DoNotReorder`, `Clearance`, unchanged
`Purchase`) instead of only ever producing `Purchase`. A new `OverstockRisk`
enum; `RecommendationType`/`InventoryRecommendation` docblocks updated to
reflect the newly-populated `overstock_risk`/`ageing_risk` columns (both
present in the schema since Phase 7, always `null` until now).

**Key decisions (including rejected alternatives and why):**

- **Ageing/overstock evaluation runs independently of the purchase path,**
  not as an afterthought bolted onto it. Phase 7's `buildRecommendation()`
  returned `null` outright for "no forecasted demand," "no primary
  supplier," and "not urgent" — all three of those are now real ageing/
  overstock opportunities instead of dead ends, since neither "don't buy
  more" nor "consider clearance" needs a supplier or urgency to be
  meaningful. Restructured the method's control flow around this rather
  than patching a special case onto the old early-returns.
- **Ageing risk score uses 2 of app_plan.md §49's 8 listed inputs** (real
  batch age from `inventory_batches`, real forecasted demand vs. current
  stock), not fabricating the other six ("product lifecycle," "replacement
  pressure," "season," "recent price changes," etc.) since none are
  computable from anything this schema tracks. Averaging exactly the two
  honest, real signals was judged better than either skipping the score
  entirely or inventing placeholder values for the rest — the same
  "narrower, honest version of the fuller plan" pattern Phase 6 already
  set for its own fallback hierarchy.
- **A new `OverstockRisk` enum, not a reuse of Phase 7's `StockoutRisk`**
  — both are the same None/Moderate/Critical shape, but reusing one enum
  for two independently-meaningful columns (`stockout_risk` vs.
  `overstock_risk`) was judged more confusing than the small duplication
  of a 3-case enum. Renaming `StockoutRisk` to something generic like
  `RiskLevel` was also considered and rejected — it would have meant
  touching already-shipped, already-tested Phase 7 code for a purely
  cosmetic reason.
- **`ageing_risk` stayed a plain string column** (no `ALTER` migration to a
  numeric type) — the column had never held data before this phase, so
  casting it to `integer` on the Eloquent model (`'ageing_risk' =>
  'integer'`) was judged a safer, purely additive choice than modifying a
  migration or adding a new one to change a column type nothing else
  depends on yet.
- **`ReducePurchase` sizes the purchase to cover only the reorder point
  itself, dropping Phase 7's review-period buffer.** An urgent-but-aging
  pair still needs *some* stock (it's genuinely about to run out), but
  piling the usual extra 14 days of buffer on top of exactly the SKU the
  ageing signal is warning about would work against the signal's own
  point. This was the one place the Phase 7 formula itself needed to
  change, not just gain a new branch.
- **`Clearance` requires both a high ageing-risk score (≥75) and low
  projected sell-through (<30%)** — not either alone. A SKU can have a high
  ageing score purely from being old stock that's still selling fine
  (batch age dominates, demand is actually healthy), which shouldn't
  trigger a clearance recommendation; requiring the sell-through
  corroboration keeps `Clearance` reserved for stock that's both old/
  low-demand *and* unlikely to move soon.
- **Thresholds (50/75-point ageing bands, 3/6-month overstock bands, 30%
  sell-through) are round numbers, explicitly not calibrated against real
  outcomes** — there's no historical "did this stock actually become dead
  inventory" data in this fresh install to calibrate against. Documented as
  a defensible starting point rather than presented as tuned.
- **No product-lifecycle classification** (app_plan.md §54's
  NEW/GROWTH/MATURE/DECLINING/END_OF_LIFE) was built as a separate concept
  — the ageing/overstock formulas read a SKU's own batch age and forecast
  directly rather than first classifying a lifecycle stage. §54 is related
  to but distinct from Phase 6's `ForecastMaturity` (which is about
  forecast confidence/data availability, not inventory risk) and wasn't
  explicitly on Phase 8's `app_plan.md` §84 "Add:" list.

## 2026-08-16 — Phase 9: multi-location optimization

**Requested:** Eighth continuation of "continue untill all phases done."
Phase 9 (app_plan.md §85): warehouse demand forecasting, branch-specific
size demand, transfer recommendation, central allocation optimization.

**Changed:** No new module — the same extend-the-existing-engine pattern
Phase 8 used on Phase 7. Two of the four §85 bullets required no code at
all: forecasts have been keyed by `(warehouse_id, sku_id)` since Phase 5,
and a `Sku` already is a specific product/variant/size, so "warehouse
demand forecasting" and "branch-specific size demand" were already true.
The other two are new:

- **Transfer recommendation** — `InventoryRecommendationService::generate()`
  restructured from a single-pass per-pair persist loop into two passes: every
  pair's candidate is built and held in memory first (keyed by `sku_id` then
  `warehouse_id`), then a new `matchTransferOpportunities()` runs across the
  whole map before anything is persisted, turning a `Purchase`/
  `ReducePurchase` candidate into `RecommendationType::TransferStock` when a
  same-SKU warehouse with real surplus (`DoNotReorder`/`Clearance`, surplus =
  `available_qty` − 90-day forecast) fully covers the need. A new nullable
  `source_warehouse_id` column on `inventory_recommendations` records which
  warehouse the transfer would come from.
- **Central allocation** — a new read-only method,
  `InventoryRecommendationService::centralAllocation()`, and a second page on
  the same controller/route group (`GET /inventory-recommendation/central-allocation`),
  grouping open `Purchase`/`ReducePurchase` rows by SKU across warehouses:
  combined quantity needed and a per-warehouse breakdown, for SKUs needed in
  two or more warehouses at once.

**Key decisions (including rejected alternatives and why):**

- **Basic version, not a solver, for transfers.** Destinations are matched
  largest-need-first against whichever remaining source has the largest
  surplus that still covers the need in full; surplus already promised to a
  bigger destination in the same run isn't available to a smaller one. **No
  partial transfers and no combining multiple sources** — if no single
  warehouse's surplus covers a destination's full need, the destination keeps
  its ordinary Purchase/ReducePurchase recommendation unchanged rather than a
  partial transfer plus a reduced purchase. Considered letting a transfer
  partially cover a need and topping up the rest with a smaller purchase, and
  rejected it: it would mean one destination pulling stock from two different
  origins (one transfer, one purchase) for the same shortfall, which doesn't
  match what `StockTransfer` (the execution module this recommendation feeds)
  expects — one source warehouse, one destination.
- **The transfer need uses the raw pre-MOQ/pre-order-multiple shortfall**
  (`_raw_need_qty`, a new transient key on the candidate array, stripped
  before persisting), not the MOQ-rounded `recommended_qty` a purchase would
  use — a transfer isn't bound by a supplier's pack size, so rounding a
  transfer up to the nearest order multiple would move more stock than
  actually needed for no reason.
- **A transfer source doesn't need a supplier configured at all** — sources
  come from the existing `DoNotReorder`/`Clearance` ageing/overstock path
  (Phase 8), which already doesn't require one. Verified directly: the test
  scenario's surplus warehouse has no `SupplierSku` row at all.
  `buildRecommendation()`'s `$base` array explicitly sets
  `'source_warehouse_id' => null` on every candidate (not just omits it) —
  the same class of bug Phase 8's `ageing_risk` schema note was careful
  about: omitting the key entirely would mean `$existingOpen->update($data)`
  never clears a stale `source_warehouse_id` left over from an earlier run
  where the pair *was* a transfer match. Caught before it became a real bug
  by writing the regression test first (`generate clears a stale transfer
  source once the surplus that backed it disappears`), which failed against
  an initial version that only set the key inside the transfer-match branch.
- **Central allocation only shows SKUs needed in two or more warehouses.** A
  SKU needed in exactly one warehouse has nothing to allocate across
  locations — it just needs an ordinary purchase, already visible on the main
  list. One consequence, confirmed in both a test and the live browser
  check: a SKU whose only two warehouses each got resolved to one
  `TransferStock` row and one `Clearance` row (no `Purchase`/`ReducePurchase`
  row left anywhere) correctly disappears from central allocation entirely —
  there's nothing left to aggregate.
- **Central allocation is a straight aggregation, not a new optimization
  formula** — each warehouse's `recommended_qty` still comes from
  `buildRecommendation()`'s own reorder-point math; this method only groups
  and sums by SKU. It does not weigh warehouse capacity, transport cost, or
  per-warehouse service-level trade-offs, since app_plan.md specifies no
  formula for any of those either. Paginated the same way
  `InventoryAnalyticsService::report()` (Phase 3) already paginates a
  computed, non-Eloquent-paginated report: a manual `LengthAwarePaginator`
  over a `Collection`, since grouping/summing has to happen in PHP after the
  query.
- **No integration wiring an accepted `TransferStock` recommendation into a
  real `StockTransfer` row** — same "decision recorded, execution is a
  separate manual step" relationship Phase 7 already left between an
  accepted `Purchase` recommendation and `PurchaseOrder`. Accept/Modify/Reject
  work identically regardless of recommendation type since `applyDecision()`
  doesn't branch on type; no controller/Service change was needed there.

**Key decisions (including rejected alternatives and why):**

- **Built both "blocked" items for real rather than working around the
  user's override with something fake.** A `Promotion` module was built
  with its own real schema (not bolted onto an existing table), and a
  genuine second forecasting algorithm was added to the Python service
  (not a duplicate of the first one under a different name) — the
  alternative (inventing a placeholder promotions concept or a second
  algorithm that's secretly identical to the first) would have violated
  "no placeholder code, no invented data" regardless of the user's answer
  authorizing the *attempt*; the answer authorized solving the problem for
  real, not faking it.
- **`ModelSelectionService::chooseAlgorithm()` requires both algorithms to
  have been scored at least once before comparing them** — picking
  whichever algorithm merely *has* history (even if the other has none)
  would be comparing against nothing, not a real comparison. Defaults to
  `ewma`, not a guess.
- **`Promotion` has no status workflow** (`Draft`/`Active`/`Cancelled`, the
  shape every other status-driven module in this app uses) — deliberately.
  "Upcoming/active/ended" is fully determined by `start_date`/`end_date`
  against today; adding a stored status field would just be a value someone
  could forget to update, duplicating what the dates already say
  authoritatively. Considered and rejected in favor of a computed
  `PromotionResource::state()`.
- **`promotion_skus` uses a plain `belongsToMany`/`sync()`, no typed pivot
  class** — unlike `variant_attribute_values` (§1a), which needed one
  because its pivot carries an extra `attribute_id` column. This pivot has
  none, so the extra class would have been pure ceremony.
- **Cannibalization is scoped to same-category pairs, not the whole
  catalog** — both a defensible business assumption (substitutes are
  usually in the same category) and what keeps an inherently O(n²)
  pairwise comparison bounded. Documented as a real scaling limitation for
  a very large catalog, not silently accepted as fine at any scale.
- **Successor detection classifies every candidate SKU's maturity
  individually** (an N+1-shaped cost) rather than batch-computing maturity
  the way `InventoryAnalyticsService`'s `weightedAgeByPair()`/`leadTimeBySku()`
  batch their own per-pair lookups — `ForecastMaturityService::classify()`
  wasn't designed for batch input, and reshaping it was judged out of
  scope for this phase; documented as a real limitation, mitigated by
  encouraging a `category_id` filter in the UI.
- **Supplier lead time is captured monthly, not nightly** like §1h's daily
  snapshots — a single day rarely has enough purchase-order volume for a
  supplier's lead time to mean anything; a full month does.
- **`quality_issue_rate` stays a real, permanently-`null` column** rather
  than being dropped from the schema — app_plan.md's own
  `supplier_performance_metrics` definition lists it, and keeping the
  column (never populated) was judged more honest than silently omitting
  a documented field versus fabricating a value for it. Same reasoning
  Phase 7 used keeping `overstock_risk`/`ageing_risk` columns present-but-
  null before Phase 8 populated them.

- **Promotions now drive demand, reversing an earlier deliberate choice.** The
  original seeder created promotions *after* the sales loop specifically so

**Bugs found and fixed during this work (all real, none caught by tests):**

- **Stale checkpoint silently evaluated.** Lightning's `ModelCheckpoint` does
  not overwrite: given an existing `best.ckpt` it writes `best-v1.ckpt` and
  leaves the old file. `evaluate.py` loaded `best.ckpt` by name — which was a
  one-epoch smoke-test checkpoint from an aborted run. Would have reported the
  wrong model's numbers as the result. Fixed both ends: `train.py` clears the
  directory first, `evaluate.py` picks newest-by-mtime and prints what it chose.
- **Validation-window leak in evaluation.** Rolling origins originally started
  at `training_cutoff`, but the window right after training is the one early
  stopping selected the checkpoint on. Now starts at `validation_cutoff`.
- **Median-vs-mean on intermittent demand.** The TFT first scored WAPE exactly
  1.0000 / bias exactly −1.0000 — the signature of all-zero predictions.
  `mode="prediction"` on QuantileLoss returns the *median*, and the median of

  Now compared against the enum; regression test added.
- **`return_y=True` crashes on the ragged final batch** (pytorch-forecasting
  concatenates y along dim=1). Actuals are now read from the source frame,
  which also gives both model families one source of truth.
- **Windows cp1252 console** cannot encode the arrow, middot or em-dash
  characters; `train.py` prints ASCII only, since `argparse` also echoes the
  module docstring.

## 2026-08-22 — Neural forecasting, experiments 1 and 2: the TFT wins, but only while fresh

**Requested:** follow-on from the entry above. Presented with the negative
result (both trained models lost to EWMA on a single quiet window), the user
chose **"Both, sequentially"**: first retrain the TFT with a count-appropriate
loss to separate architecture from loss function, then retrain with a
year-long holdout so evaluation covers a full seasonal cycle.

**Outcome:** the earlier negative result was substantially an artefact of
*how it was measured*. Corrected, a negative-binomial TFT is the best of the
four algorithms — but the margin is entirely conditional on the model being
recently trained, which reframes the recommendation. **Still not promoted
into serving**; `_ALGORITHMS` in `ml-service/app/main.py` remains unchanged.

**Experiment 1 — loss function isolated.** Same split, same seed, same
features, only the TFT's loss changed:

| TFT loss | WAPE | Bias |
| --- | --- | --- |
| quantile | 0.6278 | −0.288 |
| negative binomial | **0.5091** | **+0.009** |

19% better WAPE and the systematic under-forecasting essentially eliminated.
This confirms the loss, not the architecture, was the TFT's first problem —
a real model defect, corrected. It did not change the ranking on that window
(`ewma` still 0.3214).

**Experiment 2 — full seasonal holdout** (`--holdout-days 365`, training cut
at 2025-08-20, 11 rolling 30-day windows, 5 of them containing promotions):

| Algorithm | WAPE | Bias |
| --- | --- | --- |
| `tft` | **0.2791** | +0.036 |
| `seasonal_naive` | 0.2815 | +0.008 |
| `ewma` | 0.2925 | +0.006 |
| `deepar` | 0.3046 | +0.054 |

The TFT moved from clearly last to nominally first, which confirms
experiment 1's single window was genuinely unfair. But +0.9% is noise and
the TFT wins only 5 of 11 windows, so the pooled figure is not the answer.

**Key finding: the hypothesis was wrong, and the real driver is staleness.**
The stated reason for experiment 2 was that the TFT should earn its keep in
windows containing a promotion. That does not survive the data:

| Correlation with TFT's margin over `seasonal_naive` | Pearson r |
| --- | --- |
| Months since training cutoff | **−0.704** |
| Promotion SKU-days in window | +0.156 |

The largest-promotion window (325 SKU-days) has the TFT *losing* by 2.9%,
while it wins two promotion-free windows by ~13%. Grouping by model age
instead of by promotions:

| Model age | `tft` | best baseline | TFT margin |
| --- | --- | --- | --- |
| Fresh (windows 1–3) | **0.2597** | 0.2817 | **+7.8%** |
| 4–6 months stale | 0.2705 | 0.2603 | −3.9% |
| 7+ months stale | 0.2949 | 0.2869 | −2.8% |

A trained model decays as the forecast origin moves away from its training
data. The baselines *cannot* decay — they re-derive from the trailing 180
days on every call, which is a structural advantage no amount of training
removes. The honest conclusion is conditional: **a negative-binomial TFT
retrained at least quarterly is ~8% better than the best baseline; left
alone it drops below the baselines within about four months.** The decision
is not "which model" but "will you operate a retraining cadence" — and
nothing in this application retrains anything today.

**Decisions:**

- **Not promoted into serving**, despite now being the most accurate. The
  deciding reason is not the margin but the training data: these models learn
  `HistoricalTransactionSeeder` output, so +7.8% measures how well a TFT
  recovers that seeder's own formula, not real demand. The margin justifies
  revisiting this the moment real sales history exists. It does not justify
  shipping a model fitted to synthetic rules.
- **Reported the pooled number as misleading rather than as the headline.**
  +0.9% averages a model that is clearly better fresh with one that is clearly
  worse stale; quoting it either way would misrepresent the result.
- **`deepar` judged the weakest of the four.** Last or near-last in almost
  every window across both experiments. Its inability to use past-observed
  covariates (an autoregressive constraint in pytorch-forecasting, not a
  tuning choice) is the likely cause.

**Bugs found and fixed in this round — all silent, all would have produced
plausible but wrong numbers:**

- **Normaliser mismatch between training and evaluation.** `evaluate.py` built
  the TFT's prediction dataset with the default softplus normaliser, but a
  negative-binomial checkpoint trains against an uncentred one. Mismatched
  scaling corrupts every prediction with no error. Fixed by loading the
  checkpoint *first* and building the dataset to match its loss.
- **Split mismatch.** Same class of problem for `--holdout-days`: evaluating a
  365-day-holdout model against the default split scores the wrong windows.
  `train.py` now records its config into `training_summary.json` and
  `evaluate.py` reads it back, so the two commands cannot drift apart by hand.
  `_training_config()` tolerates the older bare-list summary format.
- **`train.py` and `evaluate.py` reported the same checkpoint differently.**
  One scored the raw median, the other an integrated expectation, so a run
  could print "TFT validation: WAPE 1.0000" and then evaluate at 0.6278 with
  nothing actually wrong. Both now share `training/prediction.py`, whose
  `point_forecast()` decides from `is_quantile_loss(model)` — read off the
  checkpoint's own loss object, never inferred from the model's name, so a
  negative-binomial TFT is not double-corrected. **Note:** this moved
  `_expected_value_from_quantiles()` out of `evaluate.py`; the previous
  task-log entry's reference to that location is now stale (that log is
  append-only, so it is corrected here rather than edited there).
- **Series-order mismatch between the two models** would have silently
  misaligned the baselines against one of them; `evaluate.py` now raises if
  the two prediction indices disagree.

## 2026-09-03 — Serving the trained model: neural inference wired end to end, retrained, and the accuracy case left unmade

**Requested:** "run AI model in app and start train and make this app 100%

**Outcome:** the trained models now run in the app. A 441-pair forecast run
against the Temporal Fusion Transformer completes in ~20s and persists 404
TFT-produced forecasts (37 pairs correctly falling back). Retraining runs
monthly. **The accuracy argument for using it on this data was not made, and
`ML_DEFAULT_ALGORITHM` is therefore left at `ewma`** — see "The honest result"
below. Everything is built, tested and one env var away from being live.

**Why the reversal was carried out rather than argued with.** The prior
decision had two stated reasons: the models learn `HistoricalTransactionSeeder`
output rather than real demand, and nothing retrained them. The second is now
solved. The first cannot be solved without real sales history and is unchanged
— it is restated in `app_guide.md`, `ml-service/README.md` and §1q rather than
quietly dropped. The user was told the caveat and asked for the work anyway,
which is their call to make.

### What was actually missing (it was not the accuracy argument)

`train.py`'s docstring claimed it wrote "the dataset parameters needed to
reconstruct the feature pipeline at serve time." **It did not.** No such code
existed. This — not the accuracy debate — is why no trained model could ever
have been served: a checkpoint alone is not a model. `TimeSeriesDataSet` holds
*fitted* state (the categorical encoders mapping a `sku_id` to an embedding row,
the per-series target normaliser, the continuous scalers), and a model fed
inputs encoded any other way returns plausible nonsense with **no error**.

`save_serving_artifacts()` now writes `models/{name}/dataset_params.pt` holding
`get_parameters()` plus `epoch_date` — needed because `time_idx` is a
known-future *real* the model reads directly (days since the training frame's
first date), so serving must resolve calendar dates to the same origin.
`neural.py` reports a checkpoint without its params as **unavailable** rather
than loading it.

### The honest result

The served checkpoint was trained on the default (minimal) split so it is as
recent as possible — correct for serving, since these models decay with age.
The cost is that only one 30-day window remains honestly scorable, and on it the
trained models **lose**:

| Algorithm | WAPE | Bias |
| --- | --- | --- |
| `ewma` | **0.3214** | +0.063 |
| `seasonal_naive` | 0.3243 | +0.098 |
| `tft` | 0.3535 | −0.051 |
| `deepar` | 0.3749 | +0.083 |

`evaluate.py` prints "Do not promote them into serving." That output was left
exactly as it is.

This is weak evidence in both directions: the window (2026-07-22 → 2026-08-20)
contains no promotion and no festival, which is precisely where the
covariate-aware models have least to offer — the same trap the 2026-08-22
experiment 1 fell into, and the reason experiment 2 (11 rolling windows over a
year) was run at all. That fair test put a *fresh* TFT ahead by ~8%. But this
checkpoint's only scorable window is negative, so the switch is left where the
evidence points. **Re-running the year-long holdout was considered and
rejected**: it costs ~2h, the answer is already recorded above, and it produces
a checkpoint deliberately a year stale — the wrong thing to serve.

**Training run:** `--tft-loss negative_binomial --max-epochs 20 --patience 4`,
default split, seed 42, CPU, ~1h35m. Validation (per-day grain): tft WAPE
1.1223 / bias −0.060, deepar 1.1630 / +0.041. Old checkpoints backed up to
`ml-service/models/_backup_20260902/`.

### Key decisions

- **`ML_DEFAULT_ALGORITHM`, defaulting to `ewma`.** The per-SKU accuracy
  comparison **cannot bootstrap itself** — a forecast is scored only after its
  horizon elapses, so on a fresh install (`forecast_accuracy` still has 0 rows)
  every SKU falls through to a default, and whatever that default is, is what
  actually runs, possibly for months. Hardcoding `ewma` there quietly meant "a
  trained model is never used, regardless of whether one exists". Making it
  configurable is what makes serving possible at all; leaving the default at
  `ewma` is what keeps this change inert until someone decides otherwise.
- **Selection now ranks on ≥2 algorithms with history, not on all of them.**
  With two candidates those rules were identical; with four, "all of them"
  means the comparison never runs.
- **The response echoes the algorithm that actually ran**, and
  `processRun()` stamps `model_version_id` from that echo rather than from what
  it requested. Load-bearing: filing a fallback under the neural model's name
  would give that model accuracy history for forecasts it never produced, and it
  could then win a comparison it never took part in.
- **Refusal, never degradation.** Unknown SKU, horizon > 30-day decoder, <45
  days of history, missing covariates, missing checkpoint — each returns a
  *baseline* with a stated reason. A run never fails because a checkpoint is
  absent.
- **Cold-start/Early pairs are forced onto a baseline in Laravel**, before the
  request. Their series has been substituted or blended with *peer* demand, and
  pairing that with this SKU's own embedding, price and category would describe
  one product using another's sales. Python would refuse a genuinely new SKU
  anyway, but not an Early SKU that *is* in the training data — the case that
  matters.
- **A pre-flight `/models` availability probe was built, wired into selection,
  and then removed from that path.** It put an extra HTTP call on every run and
  bought nothing, since the service already refuses what it cannot run. It
  survives as the diagnostic behind `app:forecast-model-status`.
- **Two HTTP timeouts, not one.** A long timeout on the baseline path would turn
  a hung service into a five-minute stall instead of a fast failure.

### Bugs found, all of which produced plausible wrong behaviour

- **`save_serving_artifacts` was defined and never called.** My own patch
  applied the function but both call sites silently failed to match, and the
  verifying grep returned only the definition — which I read as success. Caught
  when a 1h35m training run finished with no `dataset_params.pt`. Recovered
  without retraining via a new `--emit-serving-artifacts` flag that rebuilds the
  pipeline from the config recorded in `training_summary.json` (never from CLI
  flags — a mismatched `holdout_days` or `count_target` rescales every input
  silently). That flag is now the documented recovery path for any checkpoint
  predating these artifacts.
- **One `model.predict()` per series.** The first real neural run issued ~880
  Lightning trainer invocations and blew the 30s timeout with the run marked
  `Failed`. `neural.forecast_many()` now batches every series requesting the
  same model into one frame and two passes. Predictions are matched back **by
  the group id in `return_index`, never by position** — the dataloader does not
  preserve input order, and positional alignment would hand SKUs each other's
  forecasts with every number still looking plausible.
- **`seasonal_naive`'s `as_of` parameter is inert.** It changes no output value:
  `_weekday_averages` labels history backwards from `as_of - 1` while the
  horizon is read forwards from `as_of`, so a shift moves the buckets and the
  forecast days equally and cancels. Verified empirically across 28 consecutive
  origins. The behaviour is *correct* — an element's weekday is fixed by its
  offset from the end of a bare list of numbers, and nothing else is knowable —
  so nothing was changed, but `seasonal_naive.forecast`'s docstring claiming a
  wrong `as_of` "makes the model look far worse than it is" overstates it, and
  the 2026-08-22 entry's description of that fix is stronger than the code
  supports.
- **The test guarding that was structurally incapable of failing.**
  `test_a_historical_as_of_is_not_silently_aligned_to_today` asserted the two
  callers differ, guarded by "skip if today is a Saturday". The assertion cannot
  hold on any day, for the invariance reason above — so it only ever *ran* on
  non-Saturdays, and **2026-08-22, the last day the suite was run, was a
  Saturday**. It was skipped, and the suite reported 40/40. Rewritten as
  `test_as_of_does_not_change_the_prediction`, which pins the real behaviour
  across a full week.
- **Two selection tests read the developer's `.env`.**
  `ModelSelectionServiceTest`'s two "defaults to ewma" cases asserted the
  default without setting it, so once `ML_DEFAULT_ALGORITHM=tft` was set
  locally the suite failed — the result depended on local configuration rather
  than on the code. They also encoded precisely the hardcoded behaviour this
  task made configurable. Both now set `services.ml.default_algorithm`
  explicitly and are renamed to say they pin the *configured* default.
- **Snapshots lag the calendar** (data ends 2026-08-20; today is 2026-09-03).
  The serving frame anchors its forecast origin to the day after the last
  *observed* day, not `today()`. Anchoring to today leaves a gap between the
  encoder's last row and the decoder's first, which `TimeSeriesDataSet` fills by
  interpolation — inventing history rather than forecasting.

The previous entry guarded the write routes with middleware and left everything
behind them intact. That left exactly the dead weight this asks to remove: 78
routes that only ever returned 403, the controller methods behind them, 27 form
requests, 27 unreachable create/edit pages, and the service methods nothing
could call.

**Changed — everything below was deleted, not disabled:**

| Layer | Removed |
| --- | --- |
| Routes | 78 across 15 modules — `create`, `edit`, `store`, `update`, `delete`, and the purchase-order / transfer / sales-order status transitions |
| Controllers | The matching methods. Every data controller is now `index` / `all` / `get` only |
| Form requests | 27 files |
| Pages | 27 `create.tsx` / `edit.tsx` files |
| Services | `store` / `update` / `delete` / transition methods, plus the private helpers they orphaned (`totals`, `transition`, `syncValues`, `pivotData`, `syncSupplierSkus`) |
| Middleware | `ReadOnlyResource` and `BUYABANS_ALLOW_LOCAL_WRITES` — nothing left to guard |
| Enum | `MovementType::manualEntryCases()` |

~4,200 lines of PHP. Also removed the last write affordances in the UI
(Inventory's "Record adjustment", Suppliers' New/Edit/Delete, Promotions' New),
unlinked the PO / sales-order / transfer number columns that pointed at the
deleted edit pages, and rewrote the page copy that still told users to add
things they no longer can.

**Key decisions:**

- **Delete rather than guard.** A guarded route still appears in `route:list`,
  still generates a Wayfinder helper, and still has a controller, a request and
  a page behind it. It reads as live code to the next person. The reason it was
  dead does not change, so neither does its uselessness.
- **The boundary is data entry, not writes.** What survives is operations —
  syncing, starting a forecast run, scoring accuracy, capturing a snapshot or
  supplier performance, generating recommendations and recording an
  accept/modify/reject — plus the user's own account.
- **Suppliers and promotions became read-only too**, reversing the previous
  entry's exception now that the instruction was explicit. **This has a
  consequence worth stating:** supplier lead times and promotion windows have no
  source in the BuyAbans API and no entry point here, so they are frozen at
  whatever the database already holds. The reorder engine reads lead times
  directly and promotions are a forecast covariate; if either needs to change,
  it needs a source. Flagged for the user rather than assumed settled.
- **`StockMovementService::post()` kept deliberately.** It is the ledger's write
  primitive and nothing in the app calls it, but it wrote the history the
  `ledger` demand source still reads, and `InventoryDailySnapshotTest` builds
  fixtures with it. Its sibling `store()` — the manual-adjustment entry with the
  negative-stock guard — went with the route that reached it.
- **Listings, models, migrations and tables all survive.** The history in those
  tables stays readable. Deleting the stock-operation *modules* wholesale is a
  further product decision, not cleanup, and was left to the user.
- **77 tests removed, 4 recovered, 15 added.** The removed ones exercised the
  removed routes — `.ai/rules/workflow.md` requires saying that out loud. Four
  covered logic that survived (FIFO consumption and weighted-average costing
  through `post()`), so they moved to a new `StockLedgerTest` calling the Facade
  directly rather than being lost with the route. Every module suite gained a
  test asserting its write routes do not exist, which is what stops them
  quietly returning.

**Bugs and traps hit:**

- **Brace-counting over raw PHP is unsafe here.** The first method-stripper
  matched braces over raw text; an apostrophe inside a comment ("don't") opened
  a phantom string and the matcher ran past the method's real end, silently
  emptying `StockTransferService`, `SalesOrderService`, `GoodsReceiptService` and
  `SalesReturnService` of *every* method including `all()` and `get()`. Caught by
  inspecting the remaining method list rather than by any test. Restored from the
  backup and rewritten on PHP's own `token_get_all()`, which knows code from
  comment.
- **The same trap in JSX.** The promotions listing had a column keyed
  `'actions'` that held a read-only *View impact* link, not write actions. A
  name match removed it; restored after checking the backup.
- **A latent bug surfaced by removing the callers.** `StockMovementService::post()`
  writes the ledger row before applying the balance and opens no transaction of
  its own — every caller it had wrapped it. Called bare, a refused movement
  leaves the row behind. `StockLedgerTest` now asserts that as the contract,
  because it is what any future caller inherits.
- **`types:check` caught what eslint could not**, again: three pages where a
  prettier-wrapped multi-line `const` left an orphaned continuation after the
  single-line removal.
- **Stale page copy.** Removing the buttons left descriptions like "record an
  adjustment to change a balance" and "Add your first supplier" — instructions
  for actions that no longer exist. Rewritten across nine pages.
